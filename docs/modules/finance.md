# Finance module

The household budget of toon-household: toon-finance's two-person ledger, on the `finance_` tables, behind
the module contract of `docs/SPEC.md` section 2. Read this document before touching `apps/api/src/modules/finance`,
`apps/web/src/modules/finance`, `packages/shared/src/modules/finance` or the finance scripts; `CLAUDE.md` keeps the
core and cross-cutting rules and points here for everything below.

Conventions used in this document:

- **F** is toon-finance at commit `1715207` (read-only, `/home/erics/software/toon-finance`), **H** is this
  repository, **R** is toon-recipe. "F gotcha N" is F's numbering at `1715207` (see the gotcha "F gotcha
  numbers are F's numbering at `1715207`." in section 4a); "FD N" is one of F's locked decisions (section 2).
- "ledger-spec" is F's `/home/erics/software/toon-finance/docs/ledger-spec.md` (already English; the numbers
  and rules in section 1.9 are its sections 2 to 5 and agree with it); "F spec" is F's
  `/home/erics/software/toon-finance/docs/spec.md` (German). Both are referenced, not copied (SPEC D15).
- Money is integer cents everywhere (signed, on the wire as `...Cents`); the one forbidden amount is `0`.
  Timestamps are integer unix ms in SQLite and ISO strings on the wire; periods are `YYYY-MM` text.
- German UI strings are quoted byte-identical to the catalogs. Content language (what the server writes into a
  row) and interface language are two axes (F gotcha 42, section 4b).

## 1. What the module owns

### 1.1 Tables

Eleven SQL tables, all prefixed `finance_`, declared in `apps/api/src/modules/finance/schema.ts` and applied by
`apps/api/drizzle/0002_finance.sql` (generated by drizzle-kit, never by hand). The drizzle identifiers carry a
`finance` prefix because `apps/api/src/db/schema.ts` re-exports every module's schema flat and recipe owns `tags`;
ported services import them aliased (`import { financeTransactions as transactions } from "../../schema.ts"`).
Index and CHECK names carry the prefix too (SQLite index names are global).

| SQL table | drizzle identifier | F origin | What it holds |
| --- | --- | --- | --- |
| `finance_participants` | `financeParticipants` | F `household_members` (by user id) | The two seats. PK `(household_id, user_id)`, `member_slot` 1 or 2 (`finance_participants_slot_uidx` unique per household, CHECK `finance_participants_slot_range`), `display_name`, `joined_at`. `user_id` is `ON DELETE restrict`. |
| `finance_settings` | `financeSettings` | F `households.default_locale` | One row per household: `default_locale` (`de` or `en`), the language the server writes ledger text in. Written by `onHouseholdCreated`, finance enabled or not. |
| `finance_categories` | `financeCategories` | `categories` | 21 default categories per household: stable `slug`, `custom_label` null until renamed, `is_system` (`fixkosten` is not deletable or renamable), `is_hidden`, `position`. |
| `finance_tags` | `financeTags` | `tags` | Normalised tag rows with `name_key` and `usage_count` (unique per household on the key). |
| `finance_transaction_tags` | `financeTransactionTags` | `transaction_tags` | Join table, PK `(transaction_id, tag_id)`. |
| `finance_transactions` | `financeTransactions` | `transactions` | The cash book: `payer_id`, `split_mode` (`SPLIT_EQUAL`, `OTHER_ONLY`, `SETTLEMENT`), signed `amount_cents` (CHECK `<> 0`), `booked_at`, `date_source`, `origin` (`manual`, `fixed_plan`, `fixed_plan_adjustment`, `import`; no drizzle default), `plan_period`, `category_source`, `import_seq`, `external_key` (unique per household), `created_by`. |
| `finance_mutation_claims` | `financeMutationClaims` | `mutation_claims` | The replay guard of the offline queue: a client-minted `mutationId` is claimed by an INSERT on the primary key. |
| `finance_fixed_cost_items` | `financeFixedCostItems` | `fixed_cost_items` | Temporal fixed costs: `amount_cents > 0`, `active_from`, `active_to` (periods, inclusive). |
| `finance_incomes` | `financeIncomes` | `incomes` | Temporal net incomes per person: `amount_cents > 0`, `valid_from`, `valid_to`; unique `(household, person, valid_from)`. |
| `finance_fixed_cost_plans` | `financeFixedCostPlans` | `fixed_cost_plans` | One row per household: `enabled`, `payer_id`, `start_period`, `last_booked_period` (a cache for the catch-up scan, not the source of truth). |
| `finance_accrual_runs` | `financeAccrualRuns` | `accrual_runs` | Audit log of the monthly runs (`trigger` boot, interval, manual or import; counts; `error` holds only an error name). Not the idempotency mechanism. |

`financeTables` (the object of the eleven) is the manifest's `schema`. `household_id` references the core
`households.id` with `ON DELETE cascade`, so deleting a household takes the ledger with it; user references keep F's
`restrict` (payer, person, participant) or `set null` (`created_by`). Row types are `FinanceXRow` / `NewFinanceXRow`.

### 1.2 The participants model (SPEC D3)

- A household has any number of core members; **exactly two** of them take part in the ledger, as the two
  `finance_participants` rows (slot 1 and slot 2, by user id). "Exactly two" is a DB fact: the unique index and the CHECK
  on the slot, not a service convention.
- **Slot 1 anchors the balance sign** (`balanceCents > 0` means "slot 2 owes slot 1"); `slot1UserId` in
  `apps/api/src/modules/finance/services/participants/participants.service.ts` must always resolve.
- **Placeholders** (ADR 0006): a core user row without e-mail and password may be seated, in **slot 2 only**
  (`422 validation_failed` with `server.finance.placeholderSlotOne` otherwise: slot 1 anchors the balance and is the
  viewer-side default). It cannot sign in; a claim invite redeemed by registration turns the row into an account in
  place, same id, so no `payer_id`, `person_id` or seat is ever re-pointed (F gotcha 72).
- A household member **without a seat is a non-participant** and sees nothing of the ledger: every ledger route answers
  `403 finance_not_participant`, also for reads. The only route they reach is `GET .../finance/participants`
  (`{ items, viewerSlot }`, `viewerSlot: null` for them). The web shows `NonParticipantState` on every finance screen and a
  one-line Home card.
- Changing a slot is an owner or admin action (`PUT .../finance/participants`), refused while the household has any
  transaction row (`409 finance_participant_in_use`, ADR 0004); a seated participant who leaves the household is vetoed
  the same way (`409 member_has_ledger`) and otherwise loses the seat. The two rules are spelled out in section 4a.

### 1.7 Offline: persistence, outbox, service worker

- **Persisted reads** (the manifest's `persistQueryAllowList`): household segments `transactions`, `transaction`,
  `transaction-summary`, `categories`, `tags`, `plan`, `balance`, `participants` (a cold offline start must know the
  viewer's slot). Never persisted, they must be live: `plan-preview`, `plan-runs`, `balance-history`, `settlements`.
- **The outbox** is the namespace `["toon","finance","tx",<op>]` (`create`, `update`, `remove`;
  `TX_MUTATION_KEYS` in `apps/web/src/modules/finance/features/transactions/lib/offline.ts`), declared as
  `persistMutationNamespaces: [["finance","tx"]]`. Only PAUSED mutations of that namespace are persisted; plan, category
  and participant mutations never are (F gotcha 9). `mutationDefaults` is `registerTransactionMutationDefaults`
  (`setMutationDefaults`, F gotcha 7), called by `app.tsx` before the persister restores. A booking carries a `mutationId`
  minted at the call site; the API applies one `mutationId` once (`finance_mutation_claims`).
- **One service-worker rule** (`apps/web/vite.config.ts`): `NetworkOnly` for `/api/households/<id>/finance/...`, placed
  before the recipe `NetworkFirst` rule (rules are first-match). The offline copy of the ledger IS the persisted TanStack
  cache, the store the paused mutations live in; a cached `NetworkFirst` body would overwrite the optimistic row with a
  stale one (F gotcha 11).

### 1.9 Ledger rules

The domain model of F, in English. Each rule names its source section in ledger-spec and the F gotcha that guards it.
Where F's text names a person by slot ("P1", "P2") the same holds here for slot 1 and slot 2. The ledger-spec test
vectors (its section 8) are unit tests in `packages/shared/test/finance-money.test.ts`,
`packages/shared/test/finance-ledger.test.ts` and `packages/shared/test/finance-plan.test.ts`, and the API tests
`apps/api/test/finance-plan.test.ts`, `apps/api/test/finance-balance.test.ts` and `apps/api/test/finance-settlements.test.ts`.

**Storage is symmetric and "mine" does not exist** (ledger-spec §2.1; F gotcha 38, F gotcha 40). A transaction stores who
paid (`payer_id`) and how the cost is attributed (`split_mode`): `OTHER_ONLY` means "the person who is not the payer bears
100 % of this amount". With exactly two participants the other person is unambiguous, so there is no `beneficiary_id`, no
percentage rule, no `shares` table and no N-person algorithm; do not add one.

**The four kinds are a projection onto the viewer, never stored** (ledger-spec §2.2; FD1):

| UI kind (German label) | `payer_id` | `split_mode` | Who bears what |
| --- | --- | --- | --- |
| `MINE_SPLIT` ("Ich habe gezahlt, geteilt") | viewer | `SPLIT_EQUAL` | the viewer bears half plus the odd cent, the other bears half |
| `THEIRS_SPLIT` ("Partner:in hat gezahlt, geteilt") | other | `SPLIT_EQUAL` | the other bears half plus the odd cent, the viewer bears half |
| `FOR_THEM` ("Ich habe für Partner:in gezahlt") | viewer | `OTHER_ONLY` | the other bears 100 % |
| `TRANSFER` ("Ausgleichszahlung erhalten") | other | `SETTLEMENT` | pure money movement, no expense |

`kindToStorage` and `projectKind` in `packages/shared/src/modules/finance/ledger.ts` are the two directions. The same row
read from the other person's login flips the projection (a `MINE_SPLIT` of slot 1 reads as `THEIRS_SPLIT` for slot 2) with no
per-user rows. `payer = other` with `OTHER_ONLY` ("the other paid something that is 100 % mine") is representable and the
arithmetic handles it, but no UI entry point creates it.

**The balance sign convention** (ledger-spec §2.3, §5.1; F gotcha 39). `balanceCents > 0` means "slot 2 owes slot 1"; slot
1 is the anchor. For one transaction `delta = (payer is slot 1 ? +1 : -1) * owed`, where `owed` is `halfForOther(amount)` for
`SPLIT_EQUAL` and the full `amount` for `OTHER_ONLY` and `SETTLEMENT`; the balance is the sum of the deltas
(`computeBalance`; pure, total, order-independent, integer-exact). The API returns the anchor's `balanceCents` and the viewer's
`viewerBalanceCents`; **the UI never shows a raw sign**: it renders the viewer's projection through one of three catalog keys
(`finance.balance.owesYou` "{name} schuldet dir {amount}", `finance.balance.youOwe` "Du schuldest {name} {amount}",
`finance.balance.settled` "Ausgeglichen"), three keys and not three hard-wired sentences. `GET .../finance/balance` also returns a
breakdown (`splitOwnCents`, `splitOtherCents`, `forOtherCents`, `settledCents`) so the screen can say why the number is what
it is.

**`SETTLEMENT` and `OTHER_ONLY` are arithmetically identical and differ only in reporting** (ledger-spec §2.3; F gotcha 40):
`isExpense(tx) = tx.splitMode !== "SETTLEMENT"`, one exported predicate, never an ad-hoc filter. Settlements are excluded
from category totals, monthly spend and "how much did we spend on pets": they are debt movement, not consumption.

**The odd cent belongs to the payer, in both sign directions** (ledger-spec §3.2; F gotcha 32).
`halfForOther(c) = (c - (c % 2)) / 2` (JavaScript `%` takes the sign of the dividend, so this truncates toward zero) and
`halfForPayer(c) = c - halfForOther(c)`, so the two shares always add up to the amount:

| `cents` | `halfForOther` | `halfForPayer` |
| --- | --- | --- |
| 100 | 50 | 50 |
| 101 | 50 | 51 |
| 1 | 0 | 1 |
| 0 | 0 | 0 |
| -100 | -50 | -50 |
| **-101** | **-50** | **-51** |
| -1 | 0 | -1 |

**`halfForOther(-101)` must be `-50`, not `-51`.** `Math.floor(-101 / 2)` is `-51`, which would give the non-payer the larger
share of a credit while the payer carries the larger share of a cost: the odd cent would switch sides with the sign, which
positive-only tests never show and which surfaces later as drift in a ledger with negative rows. Never `Math.round(c / 2)`
(sign-inconsistent), `~~(c / 2)` (truncates above 2^31 silently) or `c >> 1` (floors negatives). Money is a signed integer
number of cents; no float touches a user amount and there is no `parseFloat` on user input (`parseGermanAmount` is an
integer-only routine for `1.234,56`, `1234,56` and `1234.56`); formatting happens at the edge of the render tree.

**Halve per transaction, not the sum** (ledger-spec §3.3; F gotcha 33). The source workbook halves a column total; the app
halves every row. They differ by 22 cents on the imported history (17 on column B, 5 on column E), and the importer reports
that difference instead of adjusting it away. Per transaction is the model because it is what the user sees on each row, it is
order-independent and it survives deleting one row without recomputing the ledger.

**The plan share is rounded once, and only the other person's** (ledger-spec §3.4, §4.2; F gotcha 34; FD3).
`share(other) = divRoundHalfAwayFromZero(income(other) * costTotal, incomeTotal)`, one integer expression with exactly one
rounding step; `payerShare = costTotal - share(other)` is the complement, so the payer carries every residual cent and the two
displayed numbers always add up to `costTotal`. Rendering `payerShare` through a second rounding call would show
`costTotal ± 1`. The quote travels as a fraction (`quoteNumerator / quoteDenominator`) and is only ever formatted
(`23,75 %`), never used as an intermediate factor. Worked example from the sheet: `costTotal = 118 750`, incomes
`301 745` and `198 255` (total `500 000`): `share(slot 2) = round(47 085.5625) = 47 086`, `share(slot 1) = round(71 664.4375) =
71 664`, `47 086 + 71 664 = 118 750`; with `costTotal = 100 001` and incomes `50 000` / `50 000` the other person's share is
`50 001` (half away from zero) and the payer carries `50 000`.

**The monthly booking** (ledger-spec §4.3). One transaction per period, `payer_id` = the plan payer, `OTHER_ONLY`, amount
`bookable(p)` = the other person's share, `booked_at` the first day of the period at 00:00 Europe/Berlin, category
`fixkosten`, tags `fixkosten` and `auto`, `external_key = fixedplan:{household}:{period}`, `origin = fixed_plan`,
`plan_period = p`, description "Fixkostenanteil MM/YYYY" (en "Fixed-cost share MM/YYYY") written in the household's default
locale. `bookable(p) = 0` writes **no row** (the amount-not-zero invariant holds for generated rows too) but still advances
`lastBookedPeriod` (F gotcha 54, below).

**The catch-up is historical and never books the future** (ledger-spec §4.5; F gotcha 35). It runs once at boot, every 6 hours
and on demand (`POST .../finance/plan/run`, `bun run plan:run`). Period `2026-03` is computed from the items and incomes that
were valid IN March even when the run happens in August (`active_from` / `valid_from` exist for this); `to` is the current
period, inclusive. A container that slept for five months books five correct rows, each with the right amount and `booked_at`.
Idempotency is the unique index on `(household_id, external_key)` with `ON CONFLICT DO NOTHING`: two concurrent runs, a
restart mid-loop or a second container converge on one row per period, and `lastBookedPeriod` is a cache that the index
overrules.

**`lastBookedPeriod` never advances over a gap** (F gotcha 45, F gotcha 54). It advances only while the run has not yet hit a
`plan_incomplete` skip (a data gap is not "already booked elsewhere" and not "the share happens to be 0"; only the first may
freeze it), and a period with share 0 does not write a row yet does advance it, so recalculation considers the set "all
periods with a plan row, plus `[startPeriod, lastBookedPeriod]`" and a period without a row diffs against 0. Otherwise a gap
or a zero period would be lost for good, with no API way back. Periods owned by a foreign origin (imported rent, manual rows)
stay exempt from recalculation.

**Booked periods are immutable** (ledger-spec §4.6; F gotcha 36; FD3). A retroactive salary change does not touch a written
row; `POST .../finance/plan/recalculate { dryRun: true }` returns a preview (`period`, `bookedCents`, `recomputedCents`,
`deltaCents`, plus the total), and on confirmation the server writes **adjustment transactions**: `OTHER_ONLY`, signed amount
`recomputed - booked`, `origin = fixed_plan_adjustment`, tags `fixkosten` and `korrektur`, `booked_at` now, description
"Korrektur Fixkostenanteil MM/YYYY", `external_key = fixedplan-adj:{household}:{period}:{bookedCents}`. The superseded amount
is in the key so that a second correction creates a second adjustment while a rerun against unchanged data conflicts and does
nothing. The diff is taken against the EFFECTIVE booked amount (the original row plus every earlier adjustment of the same
period, F gotcha 44), or a second correction would reuse the first one's key and be swallowed silently. The two people settle
against a balance both have seen; a past month that moved silently would make their settlement stop matching the ledger.

**The plan and imported history never overlap** (ledger-spec §4.7; F gotcha 46). `fixedplan:*` and `xlsx:rent:*` are different
strings, so the unique index cannot see that they name the same period. `isPeriodBooked`
(`apps/api/src/modules/finance/services/plan/plan.service.ts`) checks `(household_id, plan_period)` across every origin before
the catch-up books, and `PATCH .../finance/plan { startPeriod }` is refused (`409 plan_period_locked`) onto or before an
occupied period. Generated rows (`origin` other than `manual`) are never edited or deleted (`409 transaction_generated`);
corrections are additional rows (F gotcha 38).

**Settlements and `expectedBalanceCents`** (ledger-spec §5.3, §5.4; F gotcha 37). A settlement is a transaction with
`split_mode = SETTLEMENT`, `payer_id` = whoever hands over the money, `amount_cents` = what was handed over. `POST
.../finance/settlements` requires `expectedBalanceCents`, the balance the client displayed; if it no longer matches (the
other person booked thirty seconds ago) the answer is `409 balance_stale` carrying the current balance and the client
re-prompts. Settling against a number you were not shown is the one race in the app that costs real money. The default amount
is `|balance|` with the debtor paying (balance > 0 means slot 2 pays); part payments need no special case, and over-payment is
allowed and named (the sign flips), never clamped. The new balance is `b - sign(b) * amount`: with balance `9 842`, settling in full gives `0`, settling `5 000` gives `4 842`
and settling `15 000` gives `-5 158` (ledger-spec's vector table, §8.7 rows 57 and 58, prints `6 526` and `-3 474` for the last
two, which contradict its own §5.4 formula and toon-finance's test that asserts `4 842`; the formula is the rule). Settlements are never generated; the monthly booking creates debt, not payment.

**Idempotency of writes** (F gotchas 9, 10, 47, 73; FD6). A booking made offline replays by `mutationId`: minted at the call
site (never inside `mutationFn`, which reruns on replay), claimed on the server by an INSERT on the primary key of
`finance_mutation_claims` with `onConflictDoNothing` (not a select-then-write), and a second call answers `200` with the
current state, not `409`. The read paths behind a claim filter on the household (`peekMutationClaim` takes the household).

**Content language is the household's, not the request's** (F gotcha 42). Text the server writes into a data row (the plan
booking and adjustment descriptions, the default settlement description) follows
`finance_settings.default_locale`, never the viewer's interface language; a stored value is never re-translated on read (a
category label is interface copy until a user renames it, then content).

## 4. Gotchas

### 4a. The module's own gotchas (moved from `CLAUDE.md`)

These bind everyone who touches the module. Titles are kept as they were in `CLAUDE.md`; `CLAUDE.md` keeps a one-line
pointer to this section for the leaving rule and the greps.

- **A seated participant cannot leave while the ledger has rows.** `removeMember`
  (`apps/api/src/core/services/households/households.service.ts`) runs every build module's `onMemberRemoving(householdId,
  userId, tx)` before deleting the membership, whether or not the module is enabled for the household (rows outlive a
  disable). Finance's hook (`assertParticipantMayLeave` in
  `apps/api/src/modules/finance/services/participants/participants.service.ts`) answers `409 member_has_ledger`
  (`server.household.memberHasLedger`, toon-finance's text) when the leaver holds a slot and the household has ANY
  `finance_transactions` row or an income naming them (same predicate as the `finance_participant_in_use` replacement rule:
  every row involves both slots). Without a seat, leaving is allowed; a seated leaver with an empty ledger leaves too and the
  hook DELETES their seat (a remaining ex-member seat let the other participant book against a non-member, after which no
  admin could replace it), moving the plan payer to the remaining participant and, when the leaver held slot 1, RE-SEATING
  the survivor in slot 1 in the same transaction (M4-T01, finding A: `slot1UserId` anchors the balance and must always
  resolve); the household is then a one-seat (solo) ledger until `PUT .../finance/participants`. This is ADR 0004 and it
  replaces toon-finance's own leaving rule (F gotcha 69, ADR 0007): there is no `anchorCannotLeave` in H.
- **Plan payer and income person must be participants (M4-T01, finding B).** `PATCH .../finance/plan { payerId }` and the
  income create/update routes answer `422 validation_failed` with a field detail on `payerId` / `personId` and
  `server.finance.personNotParticipant` unless the id is one of the household's `finance_participants`; the check lives in
  the plan SERVICE (`apps/api/src/modules/finance/services/plan/plan.service.ts`, toon-finance gotcha 48), never in the route.
  Switching the plan on (`enabled: true`) checks the stored payer too (F gotcha 68).
- **Enabling finance needs two participants (D3).** `onEnable` seats the two users from the enable POST's `settings`
  (`{ participants: [{ userId, memberSlot: 1 }, { userId, memberSlot: 2 }] }`) or, on a re-enable without a body, requires
  the two existing `finance_participants` rows, else `422 finance_participants_required` and nothing is written
  (`apps/api/test/finance-module.test.ts` pins the refusal). The core stores the settings JSON in
  `household_modules.settings` and finance never reads it back: `finance_participants` is the truth, so `DELETE
  .../modules/finance` then `POST` with no body brings the ledger back intact. The web side: a manifest with `enableDialog`
  makes Home's "Aktivieren" and the Manage-modules dialog open that component instead of one direct POST
  (`apps/web/src/modules/finance/features/participants/EnableFinanceDialog.tsx`: viewer preselected as Platz 1, Platz 2
  chosen from the household's members, a one-member household gets the "Lade zuerst jemanden ein" text and no submit).
- **Finance TS identifiers carry a `finance` prefix; ported files import them aliased.** SQL names are `finance_*` (index
  and CHECK names too, e.g. `finance_transactions_household_external_key_uidx`, `finance_transactions_amount_not_zero`), the
  drizzle identifiers are `financeTransactions`, `financeCategories`, `financeTags`, `financeParticipants`, ... because
  `apps/api/src/db/schema.ts` re-exports flat and recipe owns `tags`. A ported service keeps toon-finance's body with `import
  { financeTransactions as transactions } from "../../schema.ts"`. The same trap on the shared side: finance's tag schemas and
  its 50/200 pagination are exported as `FinanceTag...` / `FinancePaginationQuery...` from
  `packages/shared/src/modules/finance/schemas/`, and consumers alias them back (`FinanceTagResponse as TagResponse`); the bare
  names are recipe's and the core's types, `request<T>` compiles with the wrong shape, so a missed alias is silent. `origin`
  keeps no drizzle default (toon-finance gotcha 38). `isUniqueViolation` (core `apps/api/src/core/services/auth/users.ts`)
  walks the error's cause chain, because drizzle wraps every query error (toon-finance gotcha 51).
- **Participants and the gate (D3, plan m3 decisions 3-5).** Exactly two `finance_participants` rows per household, by user id,
  slots 1 and 2 (unique index plus CHECK). A household member without a slot is a non-participant and sees nothing of the
  ledger: every ledger router (`transactions`, `categories`, `tags`, `plan`, `balance`, `settlements`) runs
  `requireVerifiedEmail()` then `requireFinanceParticipant()` for every method, so a non-participant gets `403
  finance_not_participant` on reads too (the kinds and the balance sign are projections onto a viewer's slot and mean nothing
  for a third person). The only route they reach is `GET .../finance/participants` (`{ items, viewerSlot }`, `viewerSlot:
  null` for them). `PUT .../participants` (admin) replaces the two (validated in the SERVICE, toon-finance gotcha 48; `409
  finance_participant_in_use` when a user leaves the budget and the household has ANY transaction row or an income naming
  them, ADR 0004; the plan payer and income person are checked against the participants, see the gotcha "Plan payer and
  income person must be participants" above), `PATCH .../participants/me` edits the own display name.
  `requireFinanceParticipant` (`apps/api/src/modules/finance/middleware.ts`) is a hoisted function declaration (API import
  cycle, see `CLAUDE.md`) and its context lives in a module-local `ContextVariableMap` augmentation. The web gate is the
  pathless `participant-gate` route under `/finance` (`FinanceGate` renders `NonParticipantState` instead of the outlet);
  Home's finance card shows the one-line state and never fires the ledger queries for a non-participant (the headless run saw
  zero 4xx for kim). `participants` is in the persist allow-list: a cold offline start must know the viewer's slot.
- **The `start` hook and the clock.** `ApiModule.start` runs once in `apps/api/src/index.ts` after `await dbReady`, never
  under `bun test`; finance awaits the boot catch-up of the fixed-cost plan and starts the 6-hour accrual tick, `shutdown`
  stops it. Every finance timestamp and the plan's `start_period` come from the module clock
  `apps/api/src/modules/finance/lib/clock.ts` (`nowMs()`, `setClockForTest`), never `Date.now()` and never the core
  `apps/api/src/core/services/households/support.ts` `nowMs`: toon-finance's plan tests pin the clock before creating the
  household and expect the plan to start in that period. A test that pins the clock hands it back with
  `setClockForTest(null)` in `afterAll` (F gotcha 4: never `mock.module`).
- **`settingsSections` are rendered.** `SettingsPage` (`apps/web/src/core/features/settings/SettingsPage.tsx`) renders each
  enabled module's `settingsSections` after the core sections (finance: `ParticipantsSection`, owners and admins change the
  two slots, a participant edits their own display name). `EnableFinanceDialog` and `ParticipantsSection` are static manifest
  imports, so they obey the shell-free import graph rule of `CLAUDE.md` ("A module owns its layout route and its static
